## 7. Object storage: Backblaze B2 integration (implemented)

- **Driver:** `src/server/storage/s3-storage.ts` (S3-compatible, signed with `aws4fetch` 1.0.20, MIT, no dependencies). Selected with `STORAGE_DRIVER=s3`; variables `S3_ENDPOINT`, `S3_REGION` (optional for Backblaze, read from the endpoint), `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. Local development keeps `STORAGE_DRIVER=local`.
- **Uploads (10 MB limit kept):** browser asks `POST /api/v1/events/:id/my-submission/files/presign` (authorization, size and file-count checks), receives a 15-minute signed URL bound to one key, one content type and the exact length, PUTs the file to the bucket, then calls `.../files/complete`. The server reads the object back and applies the full validation (extension, MIME, size, magic bytes, UTF-8, SHA-256) before attaching it; invalid objects are deleted. On local storage the presign route answers 501 and the browser uses the normal upload route.
- **Downloads:** after the usual authorization the server redirects (307) to a 60-second signed URL that forces `attachment`. The bucket stays private.
- **Deletion:** the existing remove workflow deletes the object.
- **Content-security policy:** `connect-src` gains exactly the storage endpoint origin when `STORAGE_DRIVER=s3` (read at build time from `S3_ENDPOINT`).
- **Local secrets:** `web/.env.storage` (git-ignored). `npx tsx --conditions=react-server scripts/b2-selftest.mts` runs a live test under `selftest/<random>/` only and purges every version of exactly those objects.

### Bucket settings the owner must make in the Backblaze console

1. **Lifecycle:** set the bucket lifecycle to "Keep only the last version of the file". Without it, deleting through the S3 API only hides a file and it keeps using storage.
2. **CORS** (needed for browser uploads; the page must allow the S3 API): add a custom rule allowing the site origin(s), the operations for S3 PUT, GET and HEAD, the header `content-type`, and a max age of 3600 s. Origins: the production site address (known once the host is chosen) and `http://localhost:3010` for development. The self-test reports whether a preflight from those origins is accepted.
3. Keep the bucket **Private** and the application key limited to this bucket.

## 8. Abandoned direct uploads: cleanup (implemented)

- **Ledger:** table `pending_uploads` (migration `20261119090000_pending_uploads`, **applied to the local development database only; not yet applied to Neon**). One row per signed upload: unique server-generated `storage_key`, `owner_id`, `submission_id`, `content_type`, `declared_size`, `status` (PENDING, COMPLETED, REJECTED, EXPIRED), `created_at`, `expires_at`, `resolved_at`. `submission_id` and `owner_id` have no foreign keys on purpose, so an object can still be found and deleted after its submission or user is gone. CHECK constraints keep expiry after creation, the size within 10 MB, and `resolved_at` set exactly when the row is not PENDING. The row is written in the same transaction that authorizes the upload, before any URL exists.
- **Expiry:** `PENDING_UPLOAD_TTL_MINUTES` (default 120, allowed 20 to 10080; always longer than the 15-minute URL validity).
- **Race safety:** both the completion step and the cleanup job take a row with one conditional `UPDATE ... WHERE status = 'PENDING'` (completion also requires `expires_at > now`). Exactly one wins. Completion commits its claim together with the file row, so an attached file can never be reaped; a reaped upload can never be attached (HTTP 410).
- **Job:** `POST /api/v1/internal/cleanup` (Bearer `CRON_SECRET`, now strictly requiring the `Bearer` scheme) also runs `sweepAbandonedUploads`: expired PENDING rows only, a batch of 200 per run, object deleted with all its versions, failed deletions return to PENDING and are retried, resolved ledger rows older than 30 days are removed. A second run does nothing. Every candidate is checked again against `submission_files` before deletion. It logs counts only.
- **Backblaze versions:** the S3 driver's `remove` lists the versions of the exact key and deletes each one (falls back to a plain delete if listing is not permitted). Verified live: 2 versions before, 0 after. This also makes the bucket lifecycle rule "keep only the last version" unnecessary for app deletions (still harmless to set).
- **Scheduling:** call the endpoint daily (Vercel Cron on Hobby allows once a day, or any free scheduler). **Known gap:** objects of files whose submission is deleted by cascade (for example deleting a whole event) are not reaped by this job.
- **Deploy order:** apply the new migration to Neon (`node scripts/neon.mjs deploy`, owner-approved) before deploying code that uses it.
